# 4rtofl.org のメール運用

4rtofl.org のメールは、Cloudflare の Email Worker で受け取り、Cloudflare の中に保存する。外部のアドレスへは転送しない。アドレスの追加と削除は、権限の変更と同じく、このリポジトリへの Pull Request と承認で行う。

> 現在は設計中です。Email Routing と MX レコードはまだ設定していません。

## 目的

- 4rtofl.org のメールアドレスの作成と削除を、Pull Request と承認で行う。
- 4rtofl.org 宛てのメールを、Org の外のアドレス（個人の Gmail など）に出さない。
- 契約済みの Workers Paid の範囲で運用し、メールボックスのサービスには費用をかけない。

## 構成

```
xxx@4rtofl.org ── MX は Cloudflare。キャッチオールを Email Worker に向ける
      │
      ▼
Email Worker
      ├ 振り分け表を見て、保存先の受信箱を決める
      ├ 表にないアドレス宛てのメールは受け取りを拒否する
      └ 生のメールを R2 に保存し、一覧用の情報を D1 に入れる
      ▼
受信箱の画面（別途自作する。Cloudflare Access と GitHub ログインで守る）
      │
      ▼
送信は Cloudflare Email Sending を使う
```

Cloudflare には、受信箱も、メールアプリから接続する IMAP もない。そのため、受信箱の画面は自分たちで作る。

Email Worker と受信箱の画面のコード、Terraform の定義は、すべてこのリポジトリに置く。申請、承認、反映の流れを1つにまとめるためである。コードは公開されるが、シークレットやアカウント ID はコードに含めない。

## 受信箱とアドレス

受信箱は4つで固定する。Org のメンバーは3人で、増減しない前提で設計する。

| 種類 | 数 | 読める人 | 管理方法 |
|---|---|---|---|
| admin の受信箱 | 1 | メンバー全員 | 固定 |
| メンバーの受信箱 | 3 | 本人だけ | 固定 |
| エイリアス | 必要なだけ | 届け先の受信箱を読める人 | Pull Request と承認 |

`admin@4rtofl.org` と、メンバーごとの `<名前>@4rtofl.org` は、それぞれの受信箱に直接届く。

エイリアスはサービスごとに作り、どの受信箱に保存するかを振り分け表で決める。Discord のように Org で共用するアカウントには admin に届くエイリアスを、メンバーが個人で作るアカウントにはそのメンバーに届くエイリアスを使う。エイリアスは、実際にメールを転送するのではなく、Email Worker が保存先の受信箱を選ぶだけである。そのため、Cloudflare の転送先の確認や、1つのルールに転送先を1つしか指定できない制限は関係しない。

振り分け表の例を示す。

```yaml
aliases:
  discord:       { to: admin }
  figma-member1: { to: member1 }
```

`+` を使ったアドレス（`admin+xxx@4rtofl.org` など）は使わない。Email Routing の `support_subaddress` は無効のままにし、`+` 付きのアドレス宛てのメールは受け取らない。

## エイリアスの申請と反映

1. 申請者が振り分け表を変更して、Pull Request を出す。
2. CI が、追加・削除・届け先の変更を Pull Request にコメントする。権限の定義から参照されているエイリアスを削除しようとしたら、CI を失敗させる。
3. 申請者以外のメンバー2人が承認する。承認のあとに新しい変更を push すると、承認はやり直しになる。
4. `main` にマージすると、GitHub Actions が Terraform で振り分け表を Email Worker に反映する。
5. 定期的に、Cloudflare の実際の設定とリポジトリの定義を照合する。

エイリアスは、そのアドレスで登録したアカウントのパスワードリセットを受け取る場所である。サービスを退会する前に削除すると、アカウントを取り戻せなくなる。そのため、削除は2段階に分け、まず受信を止め、退会などが済んでから定義を消す。

## セキュリティ

このリポジトリは公開されているので、エイリアスの実際のアドレス名はシークレットに置く。リポジトリに書くのは、用途と届け先の受信箱の対応だけにする。ログインに使うアドレスが推測できなければ、そのアカウントを狙った攻撃やフィッシングが難しくなる。

受信箱の画面は Cloudflare Access で守り、ログインには GitHub を使う。どのメンバーがどの受信箱を読めるかは GitHub のユーザー名で決め、これも Pull Request と承認で変更する。

Email Sending では 4rtofl.org のどのアドレスからでも送信できる。そのため、受信箱の画面の側で、自分が読める受信箱に届くアドレスからしか送れないように制限する。

HTML メールは、スクリプトなどを無害化してから表示する。この受信箱にはパスワードリセットのメールが集まるので、画面が破られると、エイリアスで登録したすべてのアカウントが危険にさらされる。

Cloudflare の API トークンは2つに分ける。Pull Request では読み取り専用のトークンで差分を出す。書き込みのできるトークンは、`main` ブランチからしか使えない Environment に置く。

Cloudflare とドメイン登録業者のアカウントには、4rtofl.org の外のアドレスでログインする。4rtofl.org のアドレスにすると、Cloudflare に入れなくなったときに、パスワードリセットのメールも Cloudflare の中に届き、復旧できなくなるためだ。

## Terraform で管理するもの

実装は Terraform で行う。管理する予定のものを次に示す。リソース名と、プロバイダーのバージョンごとの対応状況は、実装するときに確認する。

| 対象 | 内容 |
|---|---|
| Email Routing の設定 | 有効化、`support_subaddress` の無効化、MX レコード |
| キャッチオール | すべての宛先を Email Worker に向ける |
| Email Worker | コードと、シークレットとして渡す振り分け表 |
| R2 | メールの保存用バケットと、ライフサイクルルール |
| D1 | 一覧用のデータベース |
| Cloudflare Access | 受信箱の画面へのログインと、受信箱ごとの閲覧権限 |

Terraform の state には、アカウント ID やシークレットの値が平文で入るので、リポジトリにはコミットしない。state は、R2 を S3 互換のバックエンドとして使って保存する。メールの保存用とは別のバケットにし、state 用のトークンもメール用とは分ける。

terraform-provider-cloudflare の v5.26.0 には、`support_subaddress` の値が API に送られないという不具合の報告がある（[#7386](https://github.com/cloudflare/terraform-provider-cloudflare/issues/7386)）。無効のまま使うので影響はないと見込んでいるが、定期的な照合で実際の値を確認する。

## 費用

| 項目 | 費用 |
|---|---|
| 受信 | 無料 |
| 送信 | Workers Paid（月 $5）に、月 3,000 通まで含まれる |
| 保存（R2 と D1） | 3人分ならわずか |

## 制約とリスク

- 受信箱の画面、新着の通知、迷惑メール対策は自分たちで用意する。
- Email Sending は 2026年4月に公開ベータが始まったばかりで、料金と仕様が変わる可能性がある。
- 受信できるメールは 25 MiB までで、これより大きいメールは拒否される。
- 4rtofl.org のゾーンと Workers Paid は、当面は管理者の個人の Cloudflare アカウントに置く。管理者に連絡がつかない場合、変更はできなくなる。これは、承認者が不在なら承認を待つという、このリポジトリ全体の方針と同じ扱いである。

## 保管期間

メールは次の3つに分けて保存する。

| 区分 | 期間 | 内容 |
|---|---|---|
| 通常 | 1年で自動削除 | 届いたメールは、すべてまずここに入る |
| 保管 | 無期限 | 受信箱の画面で「保管」にしたもの。契約、請求書、アカウント登録の記録など |
| ゴミ箱 | 30日で削除 | 受信箱の画面で削除したもの |

区分ごとに R2 のプレフィックスを分け、ライフサイクルルールで期限が来たメールを消す。「保管」には削除のルールを設定しない。R2 ではオブジェクトの名前を変えられないので、区分を移すときは、新しいプレフィックスにコピーしてから元を消す。ライフサイクルルールの期限はオブジェクトを作った日から数えるため、ゴミ箱の30日は、ゴミ箱に移した日から数えることになる。

ライフサイクルルールは D1 の一覧用の情報を消さない。そのため、毎日動く Worker の Cron Trigger で、期限が過ぎたメールの情報を D1 から消す。

請求書や領収書を事業の取引として受け取る場合は、税法上の保存期間に合わせて「保管」にする。

## 新着の通知

新しいメールが届いたら、Discord に通知する。通知には、どの受信箱に届いたかだけを書き、差出人、件名、本文は含めない。メールの内容を Cloudflare の外に出さないためである。通知に使う Webhook の URL はシークレットに置く。

## 進め方

受信、受信箱の画面、送信の順に作る。Discord の代表アカウントは、受信箱の画面ができて、メンバー全員が admin の受信箱を読めるようになってから登録する。送信はベータの状況に左右されるので、代表アカウントの登録を送信の完成まで待たない。

### 段階1: 受信

1. Terraform の土台を作る。state 用の R2 バケットとトークンを用意し、プロバイダーのバージョンを固定する。
2. GitHub Actions を作る。Pull Request では読み取り専用のトークンで差分を出し、`main` へのマージ後に書き込み用のトークンで反映する。書き込み用のトークンは、`main` からしか使えない Environment に置く。
3. Email Routing を有効にし、`support_subaddress` を無効にして、MX レコードを設定する。
4. メールの保存用の R2 バケットと、一覧用の D1 データベースを作る。
5. Email Worker を作る。振り分け表で保存先を決め、表にない宛先のメールは拒否し、生のメールを R2 に、一覧用の情報を D1 に保存する。保存に失敗したメールを黙って捨てないようにする。
6. キャッチオールを Email Worker に向ける。
7. 振り分け表の変更を Pull Request にコメントする CI を作る。
8. 外部のアドレスから送って、受け取りと拒否の両方が想定どおりに動くことを確かめる。

### 段階2: 受信箱の画面

1. 受信箱の画面を作り、Cloudflare Access と GitHub ログインで守る。どのメンバーがどの受信箱を読めるかを定義するファイルを作り、Pull Request と承認で変更する。
2. メールの一覧と本文の表示を作る。HTML メールは無害化してから表示する。
3. 「保管」と削除の操作を作り、区分ごとのライフサイクルルールと、D1 の情報を消す Cron Trigger を設定する。
4. Discord への新着の通知を作る。
5. 迷惑メール対策を入れる。方法はこの段階で決める。
6. Discord の代表アカウントを登録する。

### 段階3: 送信

1. Email Sending のベータの状況と料金を確認する。
2. 4rtofl.org に、送信に必要な DNS レコードを設定する。
3. 受信箱の画面から送信できるようにする。自分が読める受信箱に届くアドレスからしか送れないように制限する。
